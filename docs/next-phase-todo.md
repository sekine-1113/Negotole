# Next Phase TODO

作成日: 2026-06-09

現在の実装（匿名タイムライン・ポイント・管理パネル・SEO）を土台として、次に追加すると価値があると考えられる機能の候補一覧。

---

## 優先度: 高（実装コスト低・UX 向上大）

### 1. ポイント履歴ページ
- **概要**: マイページにポイントの取得・消費の時系列ログを表示する
- **技術的根拠**: `user_point` テーブルに全記録が既に存在する。API とコンポーネント追加だけで完結
- **UX 価値**: 現状マイページは残高表示のみ。「いつ・何pt・なぜ（デイリー/キャンペーン/投稿消費）」を見せることでポイント体験に透明性が生まれる

### 2. 自分の投稿履歴（マイポスト）
- **概要**: ログイン済みユーザーが自分の投稿だけを確認できるページ
- **技術的根拠**: `post` テーブルに `userId` は保存済み。API と `/mypage/posts` ページ追加のみ
- **UX 価値**: 「タイムライン上では匿名」というコンセプトを崩さず、本人だけが自分の投稿を振り返れる。spec の「v1 スコープ外」として明示されていた自然な次のステップ

### 3. 投稿の手動削除
- **概要**: 自分の投稿履歴から投稿を削除できる機能
- **技術的根拠**: `deleted_at` カラムは全テーブルに既存（FR-015: 論理削除）。DELETE API エンドポイントと削除ボタン追加のみ
- **UX 価値**: 誤投稿への対処手段を提供する。投稿履歴（上記 #2）と組み合わせて実装するのが自然

---

## 優先度: 中（コンセプト強化・実装コスト中）

### 4. タイムラインの自動更新
- **概要**: 一定間隔（例: 30秒）でバックグラウンドポーリングし、新着投稿をタイムライン上部に差し込む
- **技術的根拠**: 現状はリロードしないと新投稿が見えない。既存の `/api/posts` をそのまま使用可能
- **UX 価値**: 「消えていく投稿をリアルタイムで眺める」という一期一会感がサービスコンセプトと直結する

### 5. 残り時間フィルター
- **概要**: タイムラインに「まもなく消える（1時間以内）」「普通（1〜6時間）」「まだある（6時間以上）」のフィルターを追加
- **技術的根拠**: `hidden_at` はクライアントに返されているので、フロントエンド側でフィルタリング可能（APIレベルの変更不要）
- **UX 価値**: 消える直前の投稿だけを読む、という新しい楽しみ方が生まれる

### 6. 投稿のシェア機能
- **概要**: 投稿ごとの固有ページ（`/post/[id]`）を作り、X (Twitter) / LINE などへのシェアボタンを実装
- **技術的根拠**: OGP 画像・メタタグは 022 で整備済み。投稿詳細ページを追加するだけ
- **UX 価値**: **投稿者名は出さず内容のみ**をシェアすることで匿名性を維持しながら外部へのバイラルを生む

## 優先度: 低（実装コスト高・長期施策）

### 7. PWA プッシュ通知
- **概要**: Service Worker を追加し、デイリーポイント付与などのタイミングで通知を送る
- **技術的根拠**: `manifest.ts` は既に実装済み。Vercel 環境でも Web Push は動作可能
- **UX 価値**: 「今日のポイントが付与されました」通知による毎日のリテンション施策

## 優先度: 高（実装コスト低・UX 向上大）※追加分

### 8. 期限切れ投稿のフェードアウト UX
- **概要**: タイムライン上でカウントダウンが 0 になった投稿をその場でフェードアウトして消す
- **技術的根拠**: `CountdownTimer` が `remaining <= 0` を検知できる。`onExpire` コールバックを追加して `Timeline` 側で `posts` state から除外するだけ
- **UX 価値**: 現状はリロードしないと消えた投稿が残り続ける。フェードアウトにより「一期一会で消えていく」というコンセプトがリアルタイムで体験できる

### 9. アクティブキャンペーンバナー
- **概要**: アクティブなキャンペーンがあるときにタイムラインやヘッダーに「現在キャンペーン中！ログインで +Xpt」のバナーを表示する
- **技術的根拠**: `getActiveCampaign()` は既に実装済み。ページ側で呼ぶだけ。未ログインユーザーへの訴求にもなる
- **UX 価値**: キャンペーン中なのにユーザーが気づかず応募しないケースを防ぐ

### 10. キャンペーン応募状況確認（管理者向け）
- **概要**: 管理者がキャンペーン別の応募者数・応募ユーザー一覧を確認できるページ
- **技術的根拠**: `campaign_application` テーブルは既存。JOIN クエリと管理ページ追加のみ
- **UX 価値**: 施策効果の計測に必要。現状キャンペーンを打っても応募人数が把握できない

## 優先度: 中（コンセプト強化・実装コスト中）※追加分

### 11. ゲストアカウントの永続化
- **概要**: ゲストログインのたびに新規ユーザーが作られる現状を改善し、同じブラウザからは同じゲストユーザーとして扱う
- **技術的根拠**: 現在の `Credentials` provider はアクセスのたびに `INSERT` する。JWT に userId を保存し、次回は既存 userId を再利用する形に変更
- **UX 価値**: ゲストがポイントを貯めても次のログインで別人になり使えなくなる問題を解消する

### 12. 投稿通報の内製化
- **概要**: 現状の Google Form へのリンク（`ReportButton`）を廃止し、DB に通報を記録して管理者が確認・対処できる仕組みに変える
- **技術的根拠**: `report` テーブル追加と管理ページ追加。`postId` + `reason` + `reportedAt` で十分
- **UX 価値**: 通報の受付状況をリアルタイムで把握でき、悪質投稿への対処が迅速になる。外部サービス依存も解消される

### 13. 管理者ダッシュボード
- **概要**: 管理パネルのトップに全体サマリー（今日の投稿数・新規ユーザー数・アクティブ投稿数・ポイント付与総数）を表示する
- **技術的根拠**: 既存テーブルへの集計クエリのみ。追加スキーマ不要
- **UX 価値**: 現状の管理パネルはリスト閲覧のみで全体感が掴みにくい。数値サマリーがあると異常検知や施策評価がしやすくなる

## 実装順の推奨

```
#1 ポイント履歴
  → #2 自分の投稿履歴
    → #3 投稿の手動削除      （#2 と同時実装が自然）
#8 フェードアウト UX          （#4 タイムライン自動更新と同時実装が自然）
#9 キャンペーンバナー          （単独で実装可能・効果が即見える）
#10 キャンペーン応募状況       （管理者向けなのでいつでも追加可能）
#11 ゲストアカウント永続化     （ゲスト体験改善・中程度の影響範囲）
#4 タイムライン自動更新
#5 残り時間フィルター
#6 シェア機能
#12 投稿通報の内製化
#13 管理者ダッシュボード
```

`#1 → #2 → #3` は既存スキーマとAPIの範囲内で完結するため、最初のフェーズとしてまとめて実装するのが効率的。
`#8・#9・#10` はそれぞれ独立して小さく実装できるため、合間に差し込みやすい。
