# Feature Specification: レート制限の追加

**Feature Branch**: `004-add-rate-limit`

**Created**: 2026-05-25

**Status**: Draft

**Input**: User description: "レート制限なしなので、追加してください。実装は次の手順以降で行うこと。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 投稿 API へのレート制限（Priority: P1）

投稿 API に対して、一定時間内に過度なリクエストを送信するユーザーからシステムを保護する。ポイントが 0 になった後も投稿試行のリクエストを大量に送れる問題に対処する。

**Why this priority**: ポイント残高が 0 のユーザーでも投稿 API へのリクエストは無制限に送れ、サーバーリソースを消費できる。DoS 攻撃への基本的な防御として最優先。

**Independent Test**: 1 分間に規定回数を超えて投稿リクエストを送信したとき、超過分が拒否されることを確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーが 1 分間に規定の上限回数まで投稿リクエストを送信したとき、**When** 次の投稿リクエストを送信すると、**Then** `429 Too Many Requests` が返り、投稿は作成されない
2. **Given** ユーザーが規定の制限に達したとき、**When** 一定時間（ウィンドウ）が経過してから再度リクエストを送ると、**Then** 正常に処理される
3. **Given** 別のユーザーが同一 IP から大量リクエストを送信しているとき、**When** 無関係のユーザーが投稿すると、**Then** そのユーザーは影響を受けない（ユーザー単位の制限）

---

### User Story 2 - 認証エンドポイントへのレート制限（Priority: P2）

ログイン試行に対してレート制限を設け、ブルートフォース攻撃を防止する。

**Why this priority**: 認証エンドポイントへの無制限アクセスはセキュリティ上のリスクだが、Google OAuth 経由のため実際のパスワード試行は存在しない。副次的なセキュリティ強化として P2。

**Independent Test**: 短時間に多数のログイン試行（コールバック呼び出し）が来た場合に制限がかかることを確認する。

**Acceptance Scenarios**:

1. **Given** 同一 IP から短時間に多数の認証リクエストが送られたとき、**When** 閾値を超えた場合、**Then** `429` が返り、それ以上の試行が制限される
2. **Given** 通常のユーザーが正常にログインするとき、**When** 制限を超えていない場合、**Then** 認証フローは影響を受けない

---

### User Story 3 - 管理者 API へのレート制限（Priority: P3）

管理者向け API エンドポイント群にもレート制限を設ける。

**Why this priority**: 管理者は信頼されたユーザーであり、誤操作・スクリプトによる意図しない大量リクエストを防ぐ。セキュリティ強化として追加。

**Independent Test**: 管理者が短時間に閾値を超えるリクエストを送ったとき、429 が返ることを確認する。

**Acceptance Scenarios**:

1. **Given** 管理者が短時間にキャンペーン API を閾値超えで呼び出したとき、**When** 閾値を超えると、**Then** `429` が返る
2. **Given** 通常の管理操作（1 件の作成・更新・削除）を行うとき、**When** 制限内であれば、**Then** 正常に処理される

---

### Edge Cases

- レート制限の判定基準がユーザー ID の場合、未認証リクエストは IP ベースで制限する
- 制限に達した後にリクエストが来た場合、残り待ち時間を `Retry-After` ヘッダーで返す
- 同一ユーザーが複数デバイスからリクエストを送る場合の動作（ユーザー単位で合算）
- サーバーレス環境でのレート制限状態の共有（複数インスタンス間での整合性）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `POST /api/posts` は、同一ユーザーが一定時間内に規定回数を超えてリクエストした場合、`429 Too Many Requests` を返さなければならない
- **FR-002**: 認証エンドポイント（`/api/auth/*`）は、同一 IP が短時間に閾値を超えてリクエストした場合、`429` を返さなければならない
- **FR-003**: 管理者 API（`/api/admin/*`）は、同一ユーザーが短時間に閾値を超えてリクエストした場合、`429` を返さなければならない
- **FR-004**: `429` レスポンスには、次にリクエスト可能になるまでの待機時間を示す情報を含めなければならない
- **FR-005**: レート制限は認証済みエンドポイントではユーザー ID 単位で適用し、未認証エンドポイントでは IP アドレス単位で適用する
- **FR-006**: レート制限の状態はサーバーレスの複数インスタンス間で共有されなければならない（インメモリキャッシュは不可）
- **FR-007**: 既存の API インターフェース（リクエスト・レスポンス形式）は変更しない（`429` 追加のみ）

### Key Entities

- **レート制限ルール**: エンドポイントグループ・制限回数・時間ウィンドウ・識別子（ユーザー ID or IP）の組み合わせ
- **制限状態**: 各識別子の現在のリクエスト数と次リセット時刻（外部ストアで管理）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `POST /api/posts` への同一ユーザーからの 1 分あたりリクエストが上限（10 回）を超えた場合、100% の確率で `429` が返る
- **SC-002**: 正常範囲内のリクエストに対して、レート制限による追加レイテンシが 100ms 未満である
- **SC-003**: 制限ウィンドウが経過した後、次のリクエストが正常に処理される（制限が自動リセットされる）
- **SC-004**: 修正後も既存の全テストが通過する

## Assumptions

- 外部の分散キャッシュ（Upstash Redis など）を利用してレート制限状態を管理する
- レート制限の閾値はコードで定数として管理する（設定 UI は持たない）
- `POST /api/posts` の上限: 10 回/分（ユーザー単位）
- 認証エンドポイントの上限: 20 回/分（IP 単位）
- 管理者 API の上限: 30 回/分（ユーザー単位）
- Vercel の Edge Network 上ではなく、Route Handler 内でレート制限を実装する（今回のスコープ）
