# Feature Specification: 投稿作成の競合状態・整合性バグ修正

**Feature Branch**: `003-fix-post-race-condition`

**Created**: 2026-05-25

**Status**: Draft

**Input**: User description: "POST /api/posts に競合状態があるため、その修正をしてください。docs/todo.mdに書いてある内容です。また、docs配下のドキュメントも更新してください。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ポイントの二重消費・マイナス残高を防ぐ (Priority: P1)

ユーザーが同時に複数の投稿リクエストを送った場合でも、ポイントが正しく管理され、残高が不正にマイナスになったり二重消費されたりしないようにする。

**Why this priority**: ポイントシステムはサービスの投稿制限の根幹であり、不整合が発生すると無制限投稿が可能になる。ユーザーが意図的・偶発的に複数リクエストを送る状況は現実に起こりうる。

**Independent Test**: 同一ユーザーが 1pt しか残っていない状態で同時に 2 件の投稿リクエストを送った場合、1 件のみ成功し、残高が -1pt にならないことを確認する。

**Acceptance Scenarios**:

1. **Given** ポイント残高が 1pt のユーザーが、**When** ほぼ同時に 2 件の投稿を送信したとき、**Then** 1 件は成功（201）し、もう 1 件は残高不足エラー（402）となり、残高は 0pt になる（-1pt にはならない）
2. **Given** ポイント残高が 0pt のユーザーが、**When** 投稿を送信したとき、**Then** 残高不足エラー（402）が返り、投稿レコードは作成されない
3. **Given** ポイント残高が十分にあるユーザーが、**When** 投稿を送信したとき、**Then** 投稿が正常に作成され、残高が 1pt 減少する（処理が失敗した場合は投稿も残高変更も両方なかったことになる）

---

### User Story 2 - 投稿とポイント消費の原子性を保証する (Priority: P1)

投稿レコードの作成とポイント消費レコードの作成が常にセットで成功・失敗する。「投稿だけ作成されてポイントが減らない」または「ポイントだけ減って投稿が作成されない」状態が存在しないようにする。

**Why this priority**: US1 と同等の重要度。現状は投稿作成後にポイント消費が失敗すると投稿だけ残り、ポイントを使わず投稿できてしまう。

**Independent Test**: 投稿作成を模擬した状況でポイント消費処理だけを意図的に失敗させたとき、投稿レコードも作成されていないことを確認する。

**Acceptance Scenarios**:

1. **Given** 有効なリクエストを送信中に、**When** ポイント消費処理が失敗したとき、**Then** 投稿レコードも残らず、残高も変化しない（両方ロールバックされる）
2. **Given** 有効なリクエストを送信中に、**When** 投稿レコード作成が失敗したとき、**Then** ポイント消費レコードも残らない

---

### Edge Cases

- ポイント残高がちょうど 1pt の状態で同時リクエストが到達した場合
- ネットワーク障害やサーバー再起動がポイント消費直後に発生した場合
- DB 接続タイムアウトが発生した場合のロールバック動作

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ポイント残高チェックとポイント消費は、他のリクエストに割り込まれない単一の原子操作として実行されなければならない
- **FR-002**: 投稿レコードの作成とポイント消費レコードの作成は、同一トランザクションとして実行され、どちらか一方が失敗した場合は両方が取り消されなければならない
- **FR-003**: 同時リクエストによってポイント残高がゼロを下回ることがあってはならない
- **FR-004**: 修正後も既存の API インターフェース（リクエスト・レスポンス形式）は変更しない
- **FR-005**: 修正後も既存のテストがすべて通ること

### Key Entities

- **user_point**: ユーザーのポイント履歴（残高は全レコードの `get_point` 合計で算出）
- **post**: 投稿レコード（`user_point` の消費レコードと必ずセットで作成される）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一ユーザーが 1pt のみ所持した状態で同時に 10 件のリクエストを送信したとき、成功は 1 件のみで残高は 0pt となる（-1pt 以下にはならない）
- **SC-002**: ポイント消費処理を強制的に失敗させたとき、投稿レコードが DB に残らない（ロールバック成功率 100%）
- **SC-003**: 修正後も既存の全テストが通過する
- **SC-004**: 通常の投稿フロー（1リクエスト）のレスポンス時間に劣化がない

## Assumptions

- ポイント残高はすべて `user_point` テーブルの集計値で管理されており、別途 `balance` カラムは持たない
- DB はトランザクション・行ロックをサポートしている（Neon PostgreSQL のため対応済み）
- 外部から直接 `user_point` テーブルを操作するパスは投稿 API 以外にも存在する（デイリーポイント付与など）が、今回の修正スコープは投稿 API のみとする
- docs 配下のドキュメント（`api.md`・`database.md`）も今回の修正内容を反映して更新する
